# CLAUDE.md

Instructions pour Claude Code (ou tout agent) travaillant sur ce dépôt.

## L'application

Wikipedia2Book crée directement un livre PDF imprimable à partir d'articles Wikipédia : un seul livre à la fois, en mémoire dans le navigateur, prêt dès l'ouverture de la page. Ne jamais parler de « projet » dans l'interface ni dans la documentation (le mot ne subsiste que dans le nom technique du modèle `Project`, voir plus bas). Le comportement de référence est documenté dans [docs/SPECIFICATIONS.fr.md](docs/SPECIFICATIONS.fr.md) : le lire avant toute modification fonctionnelle, et le mettre à jour dans le même changement si le comportement bouge. Ne jamais laisser la spec décrire une fonctionnalité qui n'existe pas dans le code, ni l'inverse.

## Principes de conception à préserver

- **Serveur sans état.** Aucune persistance disque côté serveur (pas de DB, pas de livre ni de PDF stocké). Seule exception technique : le dossier temporaire d'une génération de PDF (`tempfile.TemporaryDirectory` dans `main.build_book_pdf`), où vont les PDF recomposés et le PDF final, supprimé à la fin de la génération, en cas d'erreur ou d'abandon par le client — c'est ce qui permet les gros livres sans manquer de mémoire ; ne jamais y garder un fichier au-delà de la requête. La sauvegarde est entièrement à la charge de l'utilisateur via export/import JSON depuis le navigateur. Seule exception, voulue par l'utilisateur : `hourly_hits` dans `app/main.py`, un compteur de requêtes par heure en mémoire (48 h, aucune IP ni chemin, perdu au redémarrage), lu par `GET /api/stats/hourly` pour la page de statistiques — ne jamais l'étendre à des données identifiantes ni le persister. Seconde exception, voulue par l'utilisateur pour diagnostiquer les plantages : `generation_log` dans `app/main.py`, le journal en mémoire des 50 dernières générations (étapes, mémoire, statut ; aucun titre, aucune IP), lu par `GET /api/health/generations` et recopié ligne à ligne sur la sortie standard (`GenerationRecord`) — même règle : rien d'identifiant, rien sur disque.
- **Le contenu des articles n'est jamais reconstruit, leur format physique si.** Chaque article sélectionné est intégré via le PDF officiel Wikipédia (`/api/rest_v1/page/pdf/{titre}/{format}`, `format` = `a4`/`letter`/`legal` d'après `page_format` via `wikipedia_api.WIKIPEDIA_PDF_PAPERS`, `a4` pour tout autre format — Wikipédia ne propose que ces trois-là, en portrait, et refuse les majuscules) : texte, images, références restent ceux de Wikipédia, jamais reparsés/reconstruits en HTML (c'était du code mort, `article_parser.py`, supprimé). En revanche, depuis que « toutes les pages doivent respecter le format d'impression » a été demandé, chaque page (article, document importé, ou générée par l'app) est recomposée — mise à l'échelle et centrée, sans déformation — sur le format/orientation choisis pour le livre (`pdf_generator.fit_page_to_format`/`fit_pdf_to_format`). Ce n'est pas une régression du principe « PDF officiel conservé » : seul le contenu compte, pas la forme physique de la page source.

## Style de code — « vibe coding »

Personne ne lit ce code. Avant toute création ou modification de code, appliquer le skill `code-style` (`.claude/skills/code-style/SKILL.md`) : pas de commentaires sauf `NE PAS` et l'en-tête de licence, pas de code mort, recherche avant suppression, marqueurs de conflit, robustesse, pièges d'édition. `CITATION.cff`/`codemeta.json` décrivent la dernière version archivée sur Software Heritage, pas la version courante : ne les mettre à jour qu'avec un nouveau SWHID fourni par l'utilisateur.

## Repères d'architecture

- `app/main.py` — endpoints FastAPI, sans état.
- `app/models.py` — modèle Pydantic `Project` = l'état complet du livre. Le nom `Project` (et le format JSON exporté `{"format": "wikipedia2book-workspace", "version": 1, "projects": [...]}`) est un détail d'implémentation conservé pour la compatibilité des fichiers déjà exportés par des utilisateurs : ne pas renommer sans gérer une migration. `UploadedDocument` (image ou PDF importé par l'utilisateur, contenu en base64 dans `data_base64`) a le même rôle qu'`Article` pour l'organisation du livre — voir `BookItem` dans `book_builder.py`.
- `app/wikipedia_api.py` — unique point de contact avec MediaWiki (recherche, liens, PDF officiel). Projets acceptés : `SITES`, tiré du type `Site` de `models.py` (Wikipédia, Wikisource, Wikilivres, Wikivoyage, Wikiversité, Wikiquote, Wiktionnaire, Wikinews, tous en `<langue>.<projet>.org`) ; `Article.site` choisit l'hôte de tous les appels (page, recherche, intro, liens, PDF), seules les pages de livre restent sur Wikipédia. Ajouter un projet = `Site`, `INTERWIKI_SITES` dans `app.js`, clés `site.*` d'`i18n.js` et `site_*` de `PDF_LABELS` (licence : `share_alike`/notes de `build_license_page_html`). Clé d'article préfixée `<projet>:` hors Wikipédia (jamais pour Wikipédia, compatibilité des JSON). Toute nouvelle requête Wikipédia passe par `MediaWikiClient`, avec le même `User-Agent` et les mêmes bornes de timeout. Toutes ses requêtes passent par `MediaWikiClient._send` : sur HTTP 429/503, attente (`Retry-After` borné à `MAX_RETRY_WAIT_S`, sinon `RETRY_DELAYS_S`) **partagée par tout le client** (`_resume_at`) puis nouvelle tentative, au plus 4, puis `MediaWikiError` explicite — ne jamais appeler `self._client.get` directement. Politique robots de Wikimédia (Media API rules) imposée aux PDF par `_media_get` : **au plus 2 téléchargements simultanés pour tout le processus** (`MEDIA_CONCURRENCY`, sémaphore global par boucle asyncio via `media_limiter()`, partagé entre tous les livres) et **25 Mbit/s sur 10 s glissantes** (`MEDIA_WINDOW_BYTES`, corps lu en flux et freiné) ; `main.DOWNLOAD_CONCURRENCY` en découle. Ne jamais remonter ces limites. `USER_AGENT` suit la politique User-Agent de la WMF (`Wikipedia2Book/<VERSION> (<contacts>) httpx/<version>`). `get_book` (renvoie un `WikipediaBook` : `subtitle` = première ligne `=== … ===`, `chapters` = liste `(titre, [articles])`, titre `""` pour les articles avant le premier `;`, chapitres sans article omis; exposé par `POST /api/books/structure` et `POST /api/sources/resolve` (utilisé par le front) et par `generate-from-wikipedia-book`; quand des articles précèdent le premier chapitre, `Project.unassigned_first` place le groupe sans chapitre en tête, sans titre ni page de chapitre, dans `ordered_article_groups` comme dans `buildOrgSlots` — garder les deux alignés) lit le **wikitexte brut** de la page de livre (pas `prop=links` ni `action=parse&prop=links`, qui renvoient tous les deux les liens triés par ordre alphabétique) afin de préserver l'ordre réel des articles — vérifié en direct contre l'API live de fr.wikipedia.org pendant le développement de cette fonctionnalité; ne pas revenir à `prop=links` pour « simplifier », ça réintroduit le bug. Même raison pour `get_links` (articles liés, utilisé par `explorer.py`) : il lit le HTML rendu (`action=parse&prop=text`, via BeautifulSoup) pour garder l'ordre d'apparition dans la page, en ignorant liens rouges (`class="new"`), liens namespacés (`:` dans le titre), ancres et auto-lien. `get_subpage_book` (sommaire d'un livre de Wikilivres ou d'une œuvre de Wikisource, `SUBPAGE_BOOK_SITES`, `kind="subpages"` de `/api/sources/resolve` dès 2 sous-pages `Titre/…` liées) lit aussi le HTML rendu, pour la même raison ; `subpage_chapters` y prend comme chapitres le premier niveau de titre qui en donne au moins deux, ignore les versions imprimables et textes entiers (`FULL_TEXT_PAGES`) et, sur Wikisource seulement (`skip_parents`), les sommaires intermédiaires dont des sous-pages sont dans le livre ; côté front, `chooseSubpageBook` (`#subpageBookDialog`) demande livre entier, livre et sommaire, page seule ou annuler. `get_intro_and_creator` fait deux appels (`prop=extracts&exintro=1` puis `prop=revisions&rvdir=newer&rvlimit=1` pour la toute première révision = le créateur de la page) — pas un seul appel combiné, l'API MediaWiki ne le permet pas pour ces deux props à la fois dans un format directement exploitable.
- `app/book_builder.py` — génère uniquement couverture, table des matières, pages de chapitre et conclusion (WeasyPrint). Les pages d'articles ne sont jamais générées par l'app : toujours le PDF officiel Wikipédia tel quel, assemblé par PyMuPDF (`pdf_generator.merge_files`, `pdf_generator.BookAssembly`). `BookItem = Article | UploadedDocument` : `ordered_article_groups`/`build_toc_html` travaillent sur ce type union (articles et documents importés se réordonnent/se chapitrent de façon identique, via leur `.key`). `build_cover_html` (couverture + introduction) et `build_toc_html` (table des matières seule, accepte `article_pages`/`chapter_pages` — page de départ de chaque entrée, `None`/absent quand la numérotation est désactivée) sont **deux documents séparés**, volontairement : `main.build_book_pdf` doit pouvoir insérer la table des matières n'importe où : `project.toc_position` vaut `"start"`, `"end"` ou `"before:<clé>"` (clé d'article/document, `chapter:<id>`, ou `chapter:` pour le groupe « Sans chapitre »), résolu par `book_builder.book_slots`/`toc_slot_index` (l'interface ne propose plus que `start`/`end`, choix « Table des matières » de l'étape Édition ; `before:` reste pour l'API), et `project.table_of_contents == False` l'omet — ce découpage est ce qui permet à la position choisie d'être réellement respectée dans le PDF (avant, la table des matières faisait partie d'un seul bloc couverture+TOC toujours placé en premier, quelle que soit `toc_position`). `page_size_mm` expose le format de page calculé, pour `pdf_generator.image_to_pdf`.
- `app/pdf_generator.py` — `generate_pdf` (WeasyPrint, HTML → PDF); `merge_files` + `BookAssembly` (PyMuPDF : `merge_files` fusionne les fichiers temporaires par lots de `MERGE_BATCH` parties (`insert_pdf`, chaque lot écrit en mise à jour incrémentale du fichier fusionné, puis le document est refermé) — pas qpdf `--pages` ni `pages.extend`, qui gardent tous les objets de toutes les pages en mémoire, environ 10 fois la taille du livre (938 Mo pour 100 articles contre 130 Mo, mesuré en local, `docs/testLimitetoolforge.md`) — puis supprime aussitôt les fichiers des parties (espace temporaire limité à deux fois la taille du livre) ; `BookAssembly(merged)` rouvre le fichier fusionné, `add_outline` les signets (`OutlineEntry`, `set_toc`), `link_toc` les liens internes de la table des matières (liens provisoires supprimés, liens `LINK_GOTO` posés, rectangles convertis de l'origine en bas à gauche du PDF vers l'origine en haut à gauche de MuPDF), `stamp_page_numbers` ajoute un numéro en bas de chaque page sauf la couverture (`insert_text`, police Helvetica intégrée de MuPDF) sans relire ni réécrire le contenu — une superposition de page (`add_overlay`) faisait presque doubler la taille du livre — après que toutes les pages, déjà passées par `fit_pdf_to_format`, sont dans le fichier fusionné —, `save` écrit le PDF final sans décompresser ni recompresser les flux, `close` ferme les fichiers ; les sources doivent rester ouvertes jusqu'à `save`); `image_to_pdf` (reportlab : convertit une image importée en une page PDF unique); `internal_links` + `BookAssembly.link_toc` (pypdf puis pikepdf : la table des matières est générée par WeasyPrint avec des liens provisoires `book_builder.TOC_LINK_PREFIX + clé`, relus après l'assemblage puis remplacés par des liens internes vers la vraie page de chaque chapitre/article — WeasyPrint ne peut pas pointer vers une page d'un autre PDF, les liens doivent donc être posés après la fusion); `fit_page_to_format`/`fit_pdf_to_format` (pypdf `Transformation`/`merge_transformed_page`, après `transfer_rotation_to_content()` sur la page source : recompose n'importe quelle page — article Wikipédia, document importé, page générée par l'app — sur un format/orientation cible donné en mm, mise à l'échelle et centrée sans déformation; appelé sur **toutes** les pages (via `fit_to_file` dans `main.build_book_pdf`), y compris celles déjà au bon format : c'est `fit_page_to_format` qui décide, une page à 1 point près du format (`FORMAT_TOLERANCE_PT`) et sans rotation ne reçoit qu'un ajustement exact de sa taille, sans réécriture du contenu — le test doit rester **avant** `transfer_rotation_to_content()`, qui réécrit tout le contenu et coûte cher; les PDF d'articles sont recomposés en tâche de fond (`fitted_items`) pendant le téléchargement des suivants). Aucune de ces fonctions n'a besoin de WeasyPrint ni de GTK/Pango, mais l'import du *module* échoue quand même sur cette machine à cause du `from weasyprint import HTML` en tête de fichier — voir le contournement (stub `sys.modules`) dans `tests/test_pdf_generation.py`.
- `app/explorer.py` — BFS sur les liens internes, bornes `max_depth ≤ 3`, `max_articles ≤ 200`.
- `app/json_source.py` — `fetch_project(url)` pour `GET /api/pdf/from-json` : télécharge un livre JSON (export de l'interface, liste ou livre seul) en HTTPS, refuse tout hôte qui ne se résout pas en adresses publiques (revérifié à chaque redirection, 3 au plus), 60 Mo et 30 s au plus ; gardé en mémoire le temps de la génération, jamais sur disque. `download` (même contrôles, taille et libellé en paramètres) sert aussi à `main.fetch_remote_file` : images de fond et documents importés donnés par leur adresse (`url` au lieu de `data_base64` dans `BookImage`/`UploadedDocument`, exactement l'un des deux), retéléchargés par le serveur à chaque génération (étape `fetch_image` pour les fonds, `prepare_document` pour les documents), 15 Mo au plus, type vérifié d'après `Content-Type`, génération arrêtée avec l'adresse en cause sinon ; le JSON ne garde que l'adresse. Ne jamais assouplir ces contrôles : le serveur deviendrait un relais vers le réseau interne. Côté page, `?json=<url>` est lu par le navigateur (`fetchWorkspaceText`), pas par le serveur. De même, `?source=` (répétable) et `?wiki=` ajoutent des sources comme le champ (`addSourcesFromAddress`, question comprise pour un sommaire) ; côté serveur, `GET /api/pdf/from-source` construit le livre (`project_from_sources`, `_resolve_source` partagé avec `/api/sources/resolve`, `parse_source_line` aligné sur `parseSourceLine`) et prend un sommaire en entier sans question (`summary=1` pour garder la page de sommaire).
- `app/static/app.js` — toute la logique front, un seul fichier, pas de framework. L'état vit dans `state.project`. `articleKey()` gère aussi bien `Article` (clé `langue:id`/`langue:title:titre`) que `UploadedDocument` (clé `doc:<id>`) — `selectedArticles()` fusionne les deux pour tout ce qui touche à l'étape Organisation. `bookFileName(project)` dérive le nom de fichier (JSON et PDF) du titre du livre — ne pas revenir à un nom fixe. Le champ `#articleQuery` est un `<textarea>` : plusieurs lignes = liste de pages, chaque ligne lue par `parseSourceLine` (puces, `[[…]]`, `[texte](url)` avec parenthèses équilibrées via `markdownLinkUrl`, préfixe de langue `nl:`) puis résolue une par une par `addSourceList` via `/api/sources/resolve`; `pushArticle` ajoute sans lever d'erreur sur un doublon. Images de fond (`cover_image`/`back_image`, étape Édition) et documents importés par adresse (`#documentUrl`, étape Organisation) : un fichier choisi est lu par le navigateur et gardé en base64 ; une adresse (`https://` seulement) est gardée telle quelle et téléchargée par le serveur à chaque génération (voir `json_source.py`). Pour une page de fichier Wikimédia, `wikimediaFileUrl` appelle directement l'API `imageinfo` du wiki (`origin=*`) pour obtenir l'adresse de l'image (vignette de 2 000 px) ou du PDF original — seule exception à « tout appel MediaWiki passe par `wikipedia_api.py` » ; le serveur, lui, ne télécharge que l'adresse finale, jamais l'API MediaWiki pour ces fichiers. Étape Organisation : la liste se lit comme une suite, seule la ligne d'un chapitre se déplace et chaque article appartient au chapitre placé au-dessus de lui (`applyOrgSequence`), il n'y a plus de menu de chapitre. `suggestIntroAndAuthor(article)` est appelée uniquement quand `main_articles` passe de 0 à ≥1 (capturer `wasFirst` *avant* le `push`, pas après) ; elle ne touche jamais `introduction`/`book_author` s'ils sont déjà renseignés — ne pas la rendre plus agressive sans qu'on le demande explicitement.
- `app/static/i18n.js` — chargé *avant* `app.js` (même scope global, pas de modules ES) : dictionnaire `I18N[lang][clé]`, `t(clé, vars)` (interpolation `{nom}`), `setLanguage(lang)`, `applyTranslations()` (remplit `[data-i18n]`/`data-i18n-placeholder`/`data-i18n-title`/`data-i18n-aria-label`), `state_i18n.lang` (persisté en `localStorage`, détecté depuis `navigator.language` au premier chargement, repli sur `en`). 12 langues (`SUPPORTED_LANGUAGES`) ; `RTL_LANGUAGES` (aujourd'hui `ar`, `fa`) : `applyTranslations()` positionne `lang` et `dir` sur `<html>` — c'est le seul endroit qui le fait, ne pas le dupliquer ailleurs. Toute nouvelle chaîne visible côté front passe par `t()`, jamais de texte français en dur dans `app.js`/`index.html` — sauf les URL/valeurs d'exemple (non traduites, ce sont des URL, pas du texte). **Important** : cette langue d'interface ne couvre pas les messages d'erreur renvoyés par le serveur (`error.message` reste tel que FastAPI/Pydantic l'a produit, en français). Elle voyage en revanche jusqu'au backend pour le PDF : `streamPdf` ajoute `?language=<lang()>` à `/api/pdf/stream`, `main.build_book_pdf(project, selected, language)` la transmet à tous les `build_*_html` et aux signets. Les titres générés viennent de `book_builder.PDF_LABELS` (`pdf_label(language, clé, **vars)`), un dictionnaire Python distinct d'`i18n.js` : toute nouvelle langue doit y être ajoutée aussi (`test_i18n.PdfLabelsTest` vérifie que ses langues = `SUPPORTED_LANGUAGES` et que les clés/paramètres concordent). La page de licence est entièrement traduite (clés `license_*` de `PDF_LABELS`, dont `license_url` = acte CC localisé, `deed.zh-hans` pour le chinois). L'image Docker installe `fonts-noto-cjk` pour que le chinois/japonais ne s'affichent pas en carrés vides, et `fonts-hanazono` (HanaMinB, dans `SERIF_FONTS`/`SANS_FONTS` de `book_builder.py`) pour les caractères rares des extensions CJK B et suivantes ; les deux sont aussi dans l'`Aptfile`.

Volumes (`app.js`) : les coupures manuelles de l'étape Organisation (`project.volume_breaks`, `before:<clé>` comme `toc_position`, résolues par `volumeStarts` puis `articleSegments`, ignorées par le serveur) délimitent d'abord les volumes, puis `bookVolumes` applique `planVolumes` à chaque segment ; `/api/version` expose `article_limit` (`main.ARTICLE_LIMIT`), gardé dans `state.articleLimit` ; au-delà, `exportPdf` découpe d'office (`planVolumes`, coupure entre chapitres, documents importés non comptés) et envoie un `Project` par volume (`volumeProject` : sélection réduite au volume, titre `export.volumeTitle`, introduction au premier volume, conclusion au dernier), chacun numéroté à part par le serveur, qui n'a rien de spécial à faire. Un refus `too_many_articles` sans limite connue fournit la limite et relance en volumes. Testé dans Chromium avec `page.route`.

Relance après un plantage (`generatePdf` dans `app.js`, appelé par `exportPdf` pour le livre ou chaque volume) : `request` et `streamPdf` lèvent `ServerCrashError` pour un plantage seulement (fetch rejeté, lecture du flux rejetée, flux fini avant le PDF, HTTP 502/503/504) ; `generatePdf` attend alors `/health` (`waitForServer`) et relance la génération depuis le début, `PDF_AUTO_RETRIES` (2) fois sans rien demander, puis avec `window.confirm` (`export.retryConfirm`). Une erreur renvoyée par le serveur (`Error` simple, événement `error`) n'est jamais relancée. Testé dans Chromium avec `page.route` (flux coupé, 503, événement `error`).

Les boutons « Générer le PDF » (`#topExportButton`, `#exportButton`) ne sont **jamais** désactivés pour cause de sélection vide — seulement pendant une génération en cours (double-soumission). Le cas « rien de sélectionné » est géré par un message dans `exportPdf()`, pas par `disabled`.

`fit_page_to_format` déclenche un `pypdf.DeprecationWarning` sur `transfer_rotation_to_content()` (appelé sur une page pas encore attachée à un writer) : attendu avec `pypdf` 5/6.x, inoffensif, et hors de portée tant que `requirements.txt` épingle `pypdf` en 6.x (versions des dépendances directes figées, `==`) — ne pas « corriger » sans qu'une migration pypdf 7 soit explicitement demandée.

## Déploiement

Pas de `docker-compose.yml` dans ce dépôt : build/run via `Dockerfile` + `scripts/docker-build.sh` (injecte commit/date/auteur git pour le pied de page). Ne pas réintroduire Compose sans raison explicite de l'utilisateur.

Système de déploiement complet décrit dans `docs/SPECIFICATIONS.fr.md` sections 13.5 à 13.7. En bref : Northflank suit `main` (`Dockerfile`); Toolforge suit la branche `production-toolforge` (buildpacks : `Procfile`, `Aptfile`, `.python-version`, `toolforge-fonts.conf`; le `Procfile` positionne `WIKIPEDIA2BOOK_PLATFORM=toolforge`, qui lève les limites de téléchargement de la politique robots de Wikimédia, dont Toolforge est exempté — ne jamais le mettre dans le `Dockerfile` ). Limite volontaire de 300 articles par livre sur tous les hébergements (`main.DEFAULT_ARTICLE_LIMIT`, `main.ARTICLE_LIMIT`, choix de l'utilisateur ; 2 000 en 1.8.9 et 1.9.0), refus HTTP 413 `too_many_articles` traduit par la clé `export.tooManyArticles`, découpage en volumes par l'interface au-delà — ne pas la lever ni proposer d'autre hébergement à la place. `main.deployment_settings` lit `WIKIPEDIA2BOOK_ARTICLE_LIMIT` (`0` = pas de limite) et `WIKIPEDIA2BOOK_DOWNLOADS` (1 à `MEDIA_CONCURRENCY` hors Toolforge, 1 à 4 sur Toolforge ; toute autre valeur empêche le démarrage), posées dans le `Dockerfile` (`300` et `2`) et documentées dans le README (« Deploying your own container », réglage de la limite d'après la mémoire du conteneur), déployée par `.github/workflows/deploy-toolforge.yml` + `scripts/toolforge-deploy.sh`. Un push sur `main` ne déploie donc jamais Toolforge : ne pousser vers `production-toolforge` que sur demande explicite de l'utilisateur, en suivant le skill `deploy-production` (`.claude/skills/deploy-production/SKILL.md`). Toute dépendance système ajoutée au `Dockerfile` doit l'être aussi dans l'`Aptfile`. `.github/workflows/toolviews-stats.yml` committe chaque jour `docs/toolviews.csv`, `docs/toolforge_hourly.csv` et `docs/stats.md` sur `main` (il n'y a plus de branche `stats`), et le job `deploy` de `deploy-toolforge.yml` fait de même juste avant de redémarrer Toolforge (le redémarrage efface les journaux d'où viennent les hits par heure), tous deux via `scripts/update-stats.sh` : Northflank redéploie donc au moins une fois par jour, choix accepté par l'utilisateur. Ces fichiers sont générés : ne pas les modifier à la main, modifier `scripts/toolviews_stats.py`/`scripts/toolforge_hourly.py`/`scripts/toolviews_chart.py`. Le relevé horaire d'avant déploiement est en `continue-on-error` : ne jamais le laisser bloquer un déploiement.

## Versionnement

Le numéro de version de l'application est dans `app/version.py` (`VERSION = "x.y.z"`), repris par `app/main.py` (`FastAPI(version=VERSION)`) et par le User-Agent envoyé à Wikimédia. Avant tout commit qui touche l'application déployée, **demander à l'utilisateur** le niveau de version (patch, minor, major ou aucun) et n'appliquer le bump qu'après sa réponse ; le niveau se juge du point de vue de l'utilisateur du service PDF. Procédure complète : skill `release` (`.claude/skills/release/SKILL.md`), avec les valeurs de la section « Paramètres des skills ». Ne jamais squasher ni réécrire ce qui est déjà poussé (`main`, tags, `production-toolforge`), ni déplacer ou supprimer un tag poussé.

`main.build_book_pdf` est un générateur asynchrone qui produit les événements de progression; tout calcul bloquant y passe par `asyncio.to_thread` (recomposition des articles, `fit_to_file`), sinon le serveur entier est gelé et les messages de progression n'arrivent qu'au prochain `await` (le libellé affiché ne correspond plus à l'étape réelle). Une fois les téléchargements finis, tout le reste (rendus WeasyPrint, `BookAssembly`, numérotation, écriture) est fait par `_finish_book`, fonction synchrone exécutée dans un processus séparé par `isolation.run_isolated` (`forkserver`, `preload(['app.main'])`, progression par `report(code)` à travers un tube, processus tué si le client abandonne — d'où le `contextlib.aclosing`) : la mémoire de l'assemblage, que l'allocateur ne rendait pas au système, est libérée à chaque génération. Les tests qui remplacent `generate_pdf`/`fit_pdf_to_format` dans `main` mettent `main.ISOLATE_ASSEMBLY = False` (même fonction dans un fil d'exécution, `isolation.run_in_thread`) ; `tests/test_isolation.py` couvre le processus séparé. Il produit enfin `{"type": "done", "path": Path, "size": n}` (PDF final dans le dossier temporaire, valide tant que le générateur n'est pas fermé : les consommateurs envoient le fichier par morceaux avec `_pdf_chunks` puis appellent `aclose()`, qui supprime le dossier) : `/api/pdf` le consomme en ignorant la progression et renvoie le fichier en flux avec `Content-Length`, `/api/pdf/stream` le sérialise en NDJSON, sauf le PDF : ligne `{"type": "done", "size": n}` puis n octets bruts (plus de base64; `streamPdf` dans `app.js` lit les lignes puis les octets). Les articles sont téléchargés jusqu'à `DOWNLOAD_CONCURRENCY` à la fois (par défaut 2 hors Toolforge, imposé par la politique Wikimédia, et 4 sur Toolforge, exempté ; réglable par `WIKIPEDIA2BOOK_DOWNLOADS`, jamais au-dessus de ces valeurs hors Toolforge) (sémaphore + file `started` pour garder la numérotation des étapes); chaque PDF est recomposé, écrit dans le dossier temporaire et compté (`fit_to_file`) dès son arrivée. Les pauses de `MediaWikiClient` sur 429/503 sont signalées par `client.on_wait` (appelé seulement quand la pause commune s'allonge) : événement `{"type": "wait", "seconds"}` mis dans la même file `started`, sans incrémenter `step`, affiché en compte à rebours par `showPdfWait` (`#pdfProgressWait`, clé `progress.wait`). Toute nouvelle étape de génération doit y ajouter un `yield progress("code")`, incrémenter `total` en conséquence et ajouter la clé `progress.<code>` dans toutes les langues de `i18n.js`.

Reste un angle mort : le rendu réel par WeasyPrint et l'assemblage avec de vraies pages générées ne sont vérifiables que dans le conteneur Docker.

- `python`/`py` dans le PATH par défaut pointent vers l'alias cassé du Microsoft Store. Le vrai interpréteur est `C:\Users\<utilisateur>\AppData\Local\Programs\Python\Python312\python.exe`.
- Un virtualenv `.venv/` existe à la racine (ignoré par git) avec `requirements.txt` déjà installé : `.venv/Scripts/python.exe`.
- `import app.main` échoue nativement sur cette machine Windows : WeasyPrint a besoin des libs GTK/Pango/Cairo (`libgobject-2.0-0`, etc.) que seul le conteneur Docker installe (via `apt-get`, voir `Dockerfile`). Ce n'est pas un bug du code — ne pas essayer de « corriger » ça côté app. Pour vérifier le code qui ne dépend pas de `pdf_generator`/WeasyPrint (`models`, `book_builder`, `wikipedia_api`, `explorer`), importer ces modules directement, ils fonctionnent dans ce `.venv`.
- Pour tester la génération PDF de bout en bout (WeasyPrint inclus), il faut lancer l'app dans le conteneur Docker (`sh scripts/docker-build.sh && docker run --rm -p 8000:8000 wikipedia2book`) et dérouler le flux Sources → Organisation → Édition → export PDF.
